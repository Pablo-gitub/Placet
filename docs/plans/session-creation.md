# Creating sessions from the PWA (RF-50–53)

Status: **proposal**, no code (October 23, 2026). Written by the coordinator
during the autonomous night session; needs the maintainer's decisions below
before implementation.

## Why it is sensitive

Starting an agent from the phone is remote execution on the PC: the agent
can read and write files and run commands in the folder it starts in. The
design therefore keeps every part of the command line fixed or chosen from
closed lists, and the folder inside roots the user configured on the PC.

## What the user chooses

| Field | Source | Rule |
| --- | --- | --- |
| Provider | `claude` (first), later `codex` | closed list of configured agents with a CLI |
| Folder | an existing folder under a configured root, or a new one (RF-53) | resolved server-side with `realpath`; must stay under a root; no symlink escapes; new folder needs a second confirmation and is created by the bridge, never the backend |
| Model | closed list per provider (aliases, e.g. `sonnet`, `opus`) | never free text |
| Effort | the RF-62 list (`low`…`max`, `auto`) | never free text |
| Name | optional display name | plain text, length-limited, passed as one argv element (`--name`) |
| Temporary | on/off (RF-52) | see below |

Roots live in the bridge configuration on the PC (e.g.
`PLACET_SESSION_ROOTS=/home/paolo/Projects`), not in the database: the phone
cannot widen them.

## How it starts (Claude Code first, RF-51)

The bridge, not the backend, starts the process, under the user's account:

```
tmux new-session -d -s placet-<short-id> -c <folder> -- \
  claude --session-id <uuid> --model <alias> --effort <level> \
         --remote-control --name <name>
```

- argv list, never a shell string; `--session-id` is generated by the backend
  so the new session is known before its first hook arrives (and the request
  that created it can be bound to it).
- `--remote-control` makes it resumable from desktop, phone and web; the tmux
  pane makes RF-62 compact/effort genuine.
- Hooks and the Placet MCP server come from the user's existing configuration;
  a session whose start hook reports `mcp: missing` is shown as such (RF-27).
- The backend records a creation job (who, when, fields, outcome) audited like
  reserved commands: `pending` → `started` (the start hook for that session id
  arrived) / `failed` (bridge refused or tmux failed) / `uncertain` (no hook
  within a window).

Codex later: `codex -C <folder> -m <model>` in tmux, same job model, after a
lab check of its hooks in a tmux-started session.

## Temporary sessions (RF-52)

A temporary session is created **for one request** from an originating
session: same folder (no folder choice), chosen provider (e.g. Codex reviewing
Claude). The request is delivered as its first prompt; when its reply is
returned, the bridge ends the tmux session (`/exit`, then `kill-session` of
the tmux session it created, never a process it did not start) and Placet
marks it closed. The user can delete it from the list. Limits: at most N
temporary sessions alive (default 2), a maximum lifetime (default 2 h), and
the usage guard applies as for any request.

## Refusals

- folder outside the roots, missing (without the new-folder flow), or not a
  directory;
- provider without a CLI, model/effort outside the lists;
- too many Placet-created sessions alive (default 4);
- bridge offline: nothing is queued for later (creation is not retried).

## Tests to write first

Path traversal and symlink escape; a root removed from the config; argv
built without a shell (names with spaces, quotes, `;`); duplicate session id;
hook never arriving (uncertain); temporary session closed only when it was
created by Placet; limits; human-only endpoint.

## Decisions needed from the maintainer

1. The roots (proposal: `~/Projects` only).
2. Whether the first version includes temporary sessions or only RF-50/51/53.
3. Default model and effort, and whether Codex is in the first version.
4. Whether a creation needs passkey confirmation like reserved commands
   (proposal: yes for a new folder, no otherwise).

## Sessions requested by agents

Status: **proposal** (October 23, 2026), after the maintainer's remark that
Claude and Codex can already start sessions themselves.

### Today

Any agent with a shell can run `claude` or `codex` as the same Unix user; this
cannot be prevented. The global hooks register such a session in Placet (the
RS-09 lab did exactly this with `claude -p`), but as a session of **unknown
origin**: no parent, no purpose, no relation.

### Through Placet

1. **Tool `placet_create_session(provider, model, effort, purpose)`.** It
   starts nothing: it creates a request for the user's approval (push
   notification) showing the requesting session, provider, model, effort,
   folder (the requester's own, never chosen by the agent) and purpose.
   Provider, model and effort come from the closed lists above.
2. **The bridge starts it** after approval, with the fixed command line of
   this plan (temporary session, RF-52 limits: number alive, lifetime).
3. **Spawn ticket.** At approval Placet issues a one-time ticket
   (`plsp_` + 128 random bits, short expiry) passed to the new process in its
   environment by the bridge. The new session's SessionStart hook spools only
   the ticket's SHA-256; the backend links the session atomically: *created
   by session X, for request #N, approved by the user*. A ticket is single use
   and bound to the provider; a session presenting none stays "unknown
   origin". Tickets are redacted like RS-09 credentials.
4. **Relation proposed at birth.** Placet proposes a temporary relation
   requester → new session, **manual approval by default** for prompts and
   replies; the user can make it automatic in the PWA. It closes with the
   temporary session.
5. **Depth 1.** A session created this way cannot request another one;
   a limit on sessions alive per requester and in total.

### Sessions created outside Placet

Still listed, labelled "unknown origin", **never** given relations or grants
automatically; the user can associate them by hand as today.

### Tests to write first

Ticket reuse, expiry, wrong provider, ticket from another requester; a
session without ticket never linked; depth-1 refusal; limits; redaction of
`plsp_`; approval refused or expired starts nothing; the relation proposed
manual and closed with the session.

### Open questions

1. Whether the approval can be skipped for a requester the user trusts
   (proposal: no, at least in the first version).
2. Default lifetime and limits (proposal: 2 h, 2 per requester, 4 in total).
3. Codex as requester and as created provider: its hooks run no async
   waiter, so delivery to it goes through the bridge as today.
